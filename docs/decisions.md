# 技术决策记录（ADR）

按「当时有哪些选项、为什么选这个、代价是什么」写。被否掉的选项也留着，因为下一个接手的人最需要知道的是**为什么不能那样做**。

---

## ADR-001 不做登录，用 `X-User-Id` 头区分用户

**背景**：题面要求「10 次/天」在真实使用中准确。额度必须绑在某个用户身份上。

**选项**
1. 完整账号体系（注册/登录/session）——至少半天，且和本题要考的 Agent 能力无关。
2. 匿名 device token + 服务端下发——够用，但仍然是半天。
3. 请求头 `X-User-Id`，缺省 `demo`。

**决定**：选 3。

**理由**：额度逻辑的正确性和身份认证的强度是正交的。把账本做对（原子预占、幂等、跨天、退款），换任何认证方式都不用改一行。用半天做登录，只会挤掉 Agent 和评估集的时间。

**代价**：任何人改一个 header 就能换身份，额度可绕过。生产环境必须换成签名的 session 或 JWT。

**什么时候必须改**：上线前。这是明确的技术债，不是疏忽。

## ADR-002 额度用「只追加账本」而不是计数器

**背景**：Part A / T6 说「有用户实际使用次数超过了 10 次，也有用户投诉同一条录音被扣了两次」。

**选项**
1. `users.used_today` 计数列，`UPDATE ... SET used = used + 1`。
2. 内存计数 + 定时落库。
3. 只追加的 `usage_ledger`，当天用量 = `SUM(delta)`。

**决定**：选 3。

**理由**
- 方案 1 的「先查再改」在并发下必然超发，除非加锁；加了锁也只是把问题藏起来，出问题时没有任何审计线索。
- 方案 2 重启即丢，直接违反「准确」。
- 方案 3 里，`reserve` 是一条**带条件的单条 INSERT**：

  ```sql
  INSERT INTO usage_ledger(...)
  SELECT ?,?,1,'reserve',?,?
  WHERE (SELECT COALESCE(SUM(delta),0) FROM usage_ledger
         WHERE user_id=? AND date_local=?) < ?
  ```

  判断和写入是同一条语句，在 `BEGIN IMMEDIATE` 下不可能被打断。50 线程并发实测：正好 10 个成功，账本合计 -10，零 SQLite 错误。

**代价**：账本会一直长。按 10 次/天/人算，10 万用户一年约 3.6 亿行——需要归档策略（按月分区或冷表）。MVP 阶段不是问题，但要写在这里。

**顺带解决的问题**：退款就是再写一条 `-1`，天然可审计；`UNIQUE(user_id, date_local, job_id, reason)` 让「同一条录音扣两次」在数据库层面不可能发生。

## ADR-003 幂等键由客户端提供，服务端只保证唯一

**背景**：网络抖动导致客户端重发，是最常见的重复扣费来源。

**决定**：`POST /api/notes/*` 接受 `idempotency_key`，缺省时服务端生成一个（此时不保证幂等——客户端没给就没法保证）。键存在 `jobs.idempotency_key` 的 UNIQUE 约束上。

**理由**：把「这次请求是不是同一次」的判断权交给最了解情况的一方（客户端）。服务端只做唯一性检查，逻辑最薄。

**代价**：客户端必须真的生成稳定的键。网页端用 `时间戳+随机串`，设备端用 `machine_code + 开机计数 + 序号`——设备重启后计数会重置，所以还带了开机随机数。

**测试**：`test_replay_of_same_idempotency_key_charges_once` 连发 5 次同一个键，断言只有 1 个 job、1 条 note、账本为 1。

## ADR-004 SQLite 而不是 Postgres

**选项**：Postgres（Docker）/ SQLite。

**决定**：SQLite。

**理由**：交付物要「clone 下来就能跑」。要求面试官先装 Docker 才能看到东西，是把验证成本转嫁给对方。SQLite 的 WAL + `BEGIN IMMEDIATE` 在这个并发量级（单机、个位数 QPS）完全够用，而且 FTS5 直接给了中文子串检索能力。

**代价**：不能多实例。水平扩展时要换 Postgres——账本表结构和条件插入语义都能照搬（`INSERT ... ON CONFLICT DO NOTHING` + `SELECT ... FOR UPDATE`）。

**已经为此做的准备**：所有 SQL 都在 `infrastructure/repos.py` 一个文件里，业务层不写 SQL。

## ADR-005 记忆检索：FTS5 trigram + 字符 n-gram 向量，RRF 融合

**背景**：要做「历史问答」加分项，就得有检索。中文没有词边界，`unicode61` 分词器对中文基本无效。

**选项**
1. 接真 embedding API（OpenAI text-embedding / BGE）——效果好，但要 Key、要联网、要花钱，且离线跑不了。
2. 本地小模型（sentence-transformers）——要下载几百 MB，首次启动体验差。
3. FTS5 `trigram` + 字符 n-gram 哈希向量。

**决定**：选 3，并把 `EmbeddingProvider` 留成协议，随时可换。

**理由**：确定性、零依赖、离线可跑，且对「找包含某个人名/金额的记录」这类查询，trigram 的词法召回其实比向量更准。语义那一路只用来补「换了说法」的情况。

**踩到的坑（都写进代码注释了）**：
- trigram 至少需要 3 个字符才能匹配，1–2 字的查询必须走 LIKE 兜底。
- 直接用整个问句检索会匹配到问句本身（「我是不是说过」），必须先剥离疑问词。
- RRF 永远会给排名，必须再加一道相似度下限（0.12），否则「火星殖民」也能引出一条「买牛奶」。

**代价**：语义能力弱于真 embedding，同义改写（「报价」vs「价格」）召回不到。这一点在评估集的 q01 上体现为：能命中，但依赖的是词法而非语义。

## ADR-006 不可逆操作走挂起审批，而不是让模型自己判断

**背景**：Part A / T3 里我自己写过担心——「权限与审批的矛盾」：Agent 要替用户办事，但有些事办错了收不回来。

**选项**
1. 让模型在 prompt 里「谨慎一点」。
2. 所有写操作都要求确认——交互会变得无法忍受。
3. 工具声明 `risk`，只有 `IRREVERSIBLE` 走审批。

**决定**：选 3。

**理由**：把判断从「模型的自觉」移到「工具的类型系统」。`create_todo` 是可撤销的（删掉即可），不该打断用户；`create_calendar_event` 一旦发出去邀请就收不回，必须确认。这个分界线由人来画，不由模型每次现猜。

**实现**：`ToolRegistry.execute()` 遇到 IRREVERSIBLE 直接抛错，只有 `execute_irreversible()` 能执行它，而后者只被审批接口调用。审批有超时（600s），超时视为拒绝。

**代价**：多一次往返。对日历这种低频操作可以接受。

## ADR-007 三个 Provider，而不是只支持一家

**决定**：`scripted`（离线确定性）、`openai`（OpenAI 兼容协议）、`anthropic`。

**理由**
- `scripted` 不是玩具：它让「没有 Key 也能完整验收」成立，也让评估集有可重复的基线（每次跑分都一样，才能判断改动是变好还是变坏）。
- OpenAI 兼容协议覆盖了 OpenAI / DeepSeek / Moonshot / 智谱 / 通义，改 `base_url` 就行——国内实际部署大概率走这条路。
- Anthropic 的 wire format 不一样，单独实现正好证明 harness 真的是 provider 中立的。

**代价**：三个实现要各自维护。但接口只有一个方法，成本可控。

**明确不做的**：不内置任何「中转站」或代理地址。Key 只能由使用者自己填，`LLM_PROVIDER` 默认 `scripted`，`.env.example` 里没有任何真实值。

## ADR-008 前端不用框架、不打包

**决定**：`web/` 是三个文件（html/css/js），FastAPI 直接 `FileResponse`。

**理由**：交付物要能被一眼看懂、被改、被验证。引入 Vite + React 意味着 `node_modules` 和构建步骤，而收益只是开发者手感——对这个体量的界面不值。

**代价**：没有组件复用、没有类型检查。界面规模再涨一倍就该换，现在不该。

---

## ADR-009 Flutter 客户端只做薄壳

**决定**：App 复用后端的全部领域概念（Note / Job / Todo / Reminder），自己不做任何业务判断，`NotaClient` 是唯一和后端耦合的地方。

**理由**：Part A 里选 Flutter 的理由是「一套代码两支客户端」，不是「客户端也要有独立智能」。智能留在云端，客户端只负责采集和展示——这也符合 Part A / T3 里「cloud + app 分工」的结论。

**代价**：离线不可用。真要做离线，需要在客户端缓存最近的 note 和 todo，属于下一版。

## ADR-010 硬件不做唤醒词、不做本地推理

**决定**：ESP32 只负责采音、上传、用灯色表达状态。

**理由**：唤醒词需要常开麦克风 + 本地模型，功耗和固件体积都会失控；本地推理对这颗芯片更不现实。而「按一下」在真实场景里比「喊一声」更可控——用户在办公室喊「Hey Nota」的社交成本很高。

**代价**：必须物理接触设备。这是产品取舍，写在这里而不是藏在代码里。
